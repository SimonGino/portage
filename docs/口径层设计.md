# 个人 AI 网关 口径层设计

## 1. 定位与目标

个人自用的 AI 模型网关，从头重写（参考 new-api 思路，不 fork 代码）。客户端是各类 agent harness（Claude Code、Codex CLI、Cursor 等），核心能力 = **协议转发与转换 + API Key 生命周期 + 模型映射 + 用量记录**。明确不做多用户运营功能。

流式（SSE）与 tool calling 是及格线，不是可选项——agent harness 全程依赖这两项。

## 2. 需求口径（已锁定）

### 2.1 协议范围

入站端点：

| 端点 | 协议 | 处理方式 |
|---|---|---|
| `/v1/chat/completions` | OpenAI Chat Completions | 透传 / 转换 |
| `/v1/responses` | OpenAI Responses | 透传 / 转换 |
| `/v1/messages` | Anthropic Messages | 透传 / 转换 |
| `/v1/embeddings` | OpenAI Embeddings | 仅透传 |
| `/v1/rerank` | Jina/Cohere 风格 Rerank（硅基流动同款） | 仅透传 |

出站三种协议：OpenAI Chat Completions 兼容、OpenAI Responses（官方及 Responses-only 模型）、Anthropic。

转换矩阵（v1）：**三协议全互转**。{Chat Completions, Responses, Anthropic} 两两双向共 6 条转换路径，加同协议透传 3 条；任意入站端点可路由到任意协议的上游，方向由入站端点协议与命中渠道的**支持协议集**共同决定（v0.33 修订，原文为「由候选所在渠道的协议决定」，见 §2.3）。

| 入站 ＼ 出站 | Chat Completions 上游 | Responses 上游 | Anthropic 上游 |
|---|---|---|---|
| Chat Completions | 透传 | 转换 | 转换 |
| Responses | 转换 | 透传 | 转换 |
| Anthropic Messages | 转换 | 转换 | 透传 |

实现优先级（按个人实际使用频率排序，展开层可调）：① Anthropic→CC、Responses→CC（harness 挂第三方便宜模型，主诉求）；② Responses→Anthropic（Codex 用 Claude，sub2api 主路径可直接对照）；③ CC→Anthropic、CC→Responses（Responses-only 模型）；④ Anthropic→Responses（预计最少用，允许放到 v1 末尾）。

注：「OpenAI 兼容」各家方言有出入（usage 字段、finish_reason、流式帧行为），按渠道做小适配，不假设完全一致。

**Codex 压缩（remote compaction）口径（v0.54）**：压缩可用性按路径分档——Responses 透传渠道且上游认得 `compaction_trigger` 时天然可用（现状即可）；**转换路径（R→A / R→CC）分两步**：先止血（遇 trigger 明确报错 + drop 日志，不再静默丢弃——静默丢会让 Codex 收到 0 个 compaction item 直接 Fatal 且不重试不降级），正式修法为**本地合成**（把压缩 turn 改写成纯 summarizer、合成恰好一个自造信封的 compaction item，配套回带摘要还原与 SSE 静默期心跳；上游无 compact 端点可转发，这是唯一能让压缩真正可用的路子）。渠道加 **compaction 能力位**：Responses 形状的 wire ≠ 支持压缩，能力位为否的透传渠道对压缩 turn 同样明确拒绝。legacy v1 `POST /v1/responses/compact` 路由到 501 明确拒绝、不实现。context window 无法由网关告知 Codex（它不读网关 `/v1/models` 取窗口），靠使用文档指引 config.toml 设 `model_context_window`。实现分票与细节见展开层 v0.47 与 [#67](https://github.com/SimonGino/portage-legacy/issues/67)。

### 2.2 上游渠道

渠道在管理端动态维护，不写死。v1 初始渠道集（v0.17 已决，覆盖 v0.11）：**Anthropic 官方、OpenAI 官方、Gemini Vertex AI、阿里百炼**；DeepSeek、硅基流动、oMLX 移出初始集（运营数据，随时可加）。M0 验收用 Anthropic 官方（Claude Code）+ 百炼或 OpenAI 官方（CC 透传）。

Vertex 与百炼均走 **OpenAI 兼容端点**接入，渠道协议为 `openai`——协议矩阵与转换路径零影响（v0.17，排除「Gemini 原生第四协议」方案：矩阵 3×3 变 4×4 范围爆炸）。

每个渠道 = **支持协议集**（v0.33，原为「协议类型」单值）+ base_url + **可用模型列表（纳管，v0.12：接入点候选只能引用已纳管模型）** + **凭证池**（1..N 份上游凭证，多凭证聚合对齐 new-api，v0.11/v0.17 已决）：

- **支持协议集（v0.33）**：渠道声明它能说的上游协议，1..3 个，如 `{openai, openai_responses}` 或 `{anthropic}`。**一个上游账号只建一个渠道**——`base_url` 存的是协议子路径之前的前缀（展开层 §6.1），CC 与 Responses 本就共用同一个前缀，差的只是 `/v1/chat/completions` 与 `/v1/responses` 这个后缀，把它们拆成两个渠道等于把同一份凭证存两遍（401 自动摘除只摘中的那一份，轮换要改两处），还把协议名顶到了对外模型名的最外层（限定名 = `渠道名/模型名`）。不限定为「OpenAI 家族才能合并」：聚合型中转在同一前缀下同时提供 `/v1/messages` 是成立的，`{anthropic, openai}` 是合法集合。
- **协议可达性探测（v0.33）：只提示，不做闸。** 保存渠道时朝勾选的子路径各发一次探测，用 404/405（路由不存在）与其余状态（路由存在）区分，结果**只在管理端显示为警告**，不落库、不参与路由、不阻止保存。理由：勾错了协议集的后果是「一半端点全 404 而另一半正常」，启动闸看不见（那要发包才知道，v0.21 通则只覆盖静态可判定的）；而探测结果会过期，把一个可能撒谎的缓存放进路由路径是更坏的失败模式。
- **探测做到渠道下的模型（v0.43）**：同一颗探测按钮在子路径层之上再跑一层**模型矩阵**——启用中的纳管模型 × 各自的有效协议集（自己声明的子集，空则继承渠道全集），每格发一个**带模型名的最小真实请求**。子路径层答「协议集勾对没有」「这把凭证还活不活」（逐把凭证，v0.38），答不了 v0.40 记录的那个坑「渠道级探测全通、请求照样 404」；模型矩阵答的正是「**这个**模型在**这一侧**通不通」。三条边界：①这一层每格都花钱（`max_tokens` 压到最小），所以**只用第一把启用凭证**、只由人手点，不逐把凭证轰全矩阵；403 的格子注明探的是哪把——403 有「这把凭证没开通这个模型」的含义。②结论**三态**：通（2xx）/ 不通（404/405，模型不存在与子路径不存在合并——对使用者是同一个结论）/ 说不清（其余，原样状态码 + 我方固定词表的摘要，不带上游原文）。不做二态：把 429 画成不通、把 400 画成通都是撒谎，而探测的口径是只提示，提示就得诚实。③沿 v0.33 血统：只提示、不落库、不进路由、刷新即失；**不给「按探测结果一键回填协议子集」**——「说不清」混在三态里，一键动作会诱导人把 429 那格当成该删的，真手改烦了再议（届时口径有 v0.40 填表助手先例）。
- **模型页主从（v0.75，修订 v0.45/v0.46；标题与层级修订 v0.76）**：导航文案写「模型」，路由仍是 `/admin/channels`、`/admin/channels/:id`。渠道列表进壳的左栏中段（只在模型页出现）：搜索 + 列表 + 新建，标记仍是缺凭证 / 无协议 / 停用。主画布主语是纳管模型列表；「上游设置」「上游凭证」是抬头上的文字按钮，点开在列表上方展开 sunken 井，默认收起。新建渠道时主区整页是表单，没有模型列表。启停开关在渠道名旁立刻生效。探测按钮仍在凭证井标题旁。选中项进 URL，刷新与回退都留在同一个渠道上。左栏**不重复**主画布已有的协议集 / 模型数 / 凭证计数。接入点 / API Key / 调用记录 / 排行维持扁平表格。**v0.76**：页标题与导航同名、不加副标题；主画布里渠道是身份条、主语仍是纳管模型列表；获取模型列表与手动添加是页头组合按钮。主语没变（仍是纳管模型），变的是标题文案和层级。
- **右栏分三段：渠道 / 上游凭证 / 模型（v0.46，段名 v0.48 由「API 密钥」改定；v0.75 把设置与凭证收进井）**，凭证池由弹框改为常驻段，「检测」按钮跟在上游凭证的段标题上——子路径层探测逐把凭证探（v0.38），结论离被它评价的那份列表越近越好；模型矩阵则跟着模型段走。渠道启停挪到渠道名旁的开关上（原先是表单里一个要点保存才生效的复选框）。左栏加搜索（匹配渠道名与 base_url，后者不显示——同一家上游在不同中转下会重名）。**Base URL 下面给出拼好的完整地址预览**（逐协议一行）：`base_url` 存的是子路径之前的前缀，填成 `…/v1` 会拼出 `/v1/v1/chat/completions`，这是必踩的坑，而只有把拼出来的那一串摆在眼前，提示文案才真的被读到。新增凭证的输入框给一个「显示」——粘错前后引号或换行的表现是保存成功但全部 401，看一眼是最省事的自检（v0.47 之后列表里本来也能看，这个「显示」省的是「先提交再回头找」这一步）。
- **子路径层探测把非 2xx 的状态翻成一句话（v0.45）**：判据不变（404/405 = 路由不存在，其余 = 路由存在），但「路由在」与「这把凭证打过去被 401」是两件事，只报前一句会让一个每条子路径都回 401 的渠道在页面上显示「探测通过」。401/403/429/5xx 各带一句我方固定词表的摘要；400 不算——探测发的是空 `{}`，被参数校验拒掉正是它预期的成功形态。**摘要不带上游原文**，与 v0.43 ②、`call_logs.error` 同一条纪律。模型矩阵那一层的摘要同时从 tooltip 挪到屏幕上：`? 429` 四个字符本身不解释任何事，而没人会去悬停一片自己看着还行的网格。
- 凭证类型渠道级二选一（v0.17）：`api_key`（静态 key，默认）/ `service_account`（GCP SA JSON → access token 定时刷新，Vertex 用；参考 new-api `relay/channel/vertex/service_account.go`）。
- 选取模式渠道级配置：`polling`（轮询，默认）/ `random`，**单选按钮放在凭证池管理面里、池中 ≥2 把（含停用）才显示**（v0.44 修订 v0.38 ⑨ 的「露在渠道表单」；露出来的立论不变——多凭证放开后「为什么总是第一把在跑」是必然要问的第一个问题，答案不能只藏在 SQL 里——但选取模式描述的是「多把 key 之间怎么轮」，它的家在 key 列表旁边，而单 key 渠道从头到尾不该看到这个概念）。
- **渠道并发上限（v0.49）**：渠道级可选配置，限制**同时打向该上游的 in-flight 请求数**；管理端手填正整数，**空/0 = 不限（默认）**，存量渠道零变化。为自部署上游而设：SGLang 这类推理引擎的准入只看显存、等待队列默认无界，过载形态是**排队堆积**而不是报错（实测 100+ 请求挂住不返回、客户端超时，靠重启清队列），上游自己缺的那层保护由网关补。三条边界：①**只做并发，不做 RPM/TPM**——LLM 请求时长方差极大，RPM 限不住堆积（10 QPS 持续放行照样能在上游堆出 100+ 并发）；TPM 依赖事后才知道的 usage，做不了准入判断。②**粒度只到渠道级**——资源瓶颈（显存、队列）在上游实例级不在模型级；模型级/凭证级将来可从渠道级下探，反过来不行。③**与全局令牌桶（§2.7）保留并存、职责不同**：全局桶限「每秒进网关的请求数」保护网关自身，本闸限「同时在上游跑的请求数」保护上游，量纲不同不打架。超限行为 v0.50 已决（见下条）；观测未决，见 §5。
- **闸满行为：网关侧有界排队（v0.50）**：并发闸打满时新请求在网关排队等空位——**队列上限默认 = 并发上限 ×1、等待超时默认 30s**，两者是 config.yaml 全局项**不进渠道表**（个人网关配置最少化；真出现渠道间要不同队列策略再升渠道列，从全局降渠道容易，反过来是删列）。队满或等超时回 **429**：错误体按入口协议原生格式、文案我方固定词表不带上游原文（两条既有纪律的顺延）、`Retry-After` 固定默认 10s 可调——1s 对「并发满」是撒谎（一个 LLM 请求几十秒，1 秒后重试大概率还满），动态估算依赖尚不存在的时长统计，等观测落地再议。**立即拒绝不取**：M0 实测 Codex 对 429 一次即弃（v0.19），harness 突发齐射的峰值几秒即过，为峰值拒请求不值；**无界等待也不取**——那正是上游这次挂掉的病因，把病搬进网关等于白做，上限与超时是这个设计的核心不是附件。排队发生在**向上游转发之前**、客户端尚未收到任何字节；`ttft_ms` 维持「网关收到请求 → 首字节回客户端」的体感语义、排队时间计入（「纯上游 ttft」将来靠观测字段相减，不为它改定义——剔除排队会造出「ttft 好看但客户端等了 40 秒」的自相矛盾流水）。网关自产 429 与上游透传 429 在流水里可区分，归因走 error 词表（v0.52，见下方观测条目）。
- **拥塞期行为：不加机制（v0.51）**：上游拥塞期与重启回暖期，网关在并发闸 + 有界排队（v0.49/v0.50）之外**不再加任何东西**——渠道级熔断与自动探活恢复明确列为非目标（§3），这是对 v0.38 无熔断范式与「探测不参与路由」两条口径的**正面审视后重申**，不是默认沿用。立论：①拥塞在网关侧的典型形态是**超时**——网关对上游刻意不设整体超时（长流会被掐断）但 `ResponseHeaderTimeout` 120s 兜底，卡在上游队列里的请求最多占闸坑 120s；而超时本就不重试（v0.19 判据：刚超时的对端原地重试大概率再超时），现有逻辑没有重试放大。②队满 503（SGLang 设 `--max-queued-requests` 后的形态）走同凭证退避重试（最多共 3 次打、带退避、不换凭证），且重试发生在同一个闸坑内不增加 in-flight（v0.50），放大被闸封顶——重试策略同场裁定**不动**，收敛 5xx 重试反而退化正常场景的瞬时抖动自愈。③单上游无处可转移，熔断省下的只是打向已死上游的少量请求，代价却是引入跨请求时间态；回暖期并发闸天然限流——重启后最多放行「并发上限」个请求，雪崩重现不出来。
- **并发闸的观测与验收（v0.52）**：观测走**流水，一列两词**——`call_logs` 加 `queue_wait_ms`（过闸请求都记，没闸/没等为 0；等到超时被拒的行记下实际等待），归因**不加新列**，往既有 error 固定词表加 `queue_full`（队满即拒）与 `queue_timeout`（等到超时）两词。至此三种 429 在流水里全分得开：`rate_limited` = 全局桶、`queue_full`/`queue_timeout` = 渠道闸、status 429 且 error 列空 = 上游透传（透传成功不算网关侧错误、error 留空是 v0.28 的既有纪律）；「纯上游 ttft」= `ttft_ms - queue_wait_ms`，v0.50 的预设兑现。**管理端不做实时 in-flight/拒绝率展示**（v1）——流水聚合已能回答「闸在不在保护、挡了多少」，实时数是内存态、要新开管理端接口去读信号量，后加成本低，真想要再说。**不消费上游（SGLang Prometheus）指标**——机制半边 v0.51 已封（会过期的缓存进路由），展示半边同样不做：网关保持自包含，上游侧自有监控，列非目标（§3）。验收以 Go 集成测试为准（§9 既有形式），四条断言见展开层 §7.5；真机对照（压测后看 `sglang:num_running_reqs` 是否被压在上限内）是部署检查项，不进仓库。
- **只有 401 自动摘除单把凭证**（v0.38 修订 v0.11 的「401/403 都摘」），记原因与时间，**只人工恢复**；403 仍在渠道内换凭证重试但**不摘任何一把**；429/5xx 不摘（容量/瞬时问题，交给同候选重试与故障转移）。凭证级摘除不违反候选层「不探测、不记忆、不摘除」——那是健康探测约束，这是配置正确性问题。三条立论：
  - **403 不摘**：403 在上游有两种含义，凭证被封（该摘）与**这把凭证没开通这个模型**（不该摘——问题只在一个模型上，摘掉的却是渠道级资源，百炼、Vertex 都是后者高发地）。误伤后果不对称，而漏网后果很轻：坏凭证顶多每次多试一轮就换掉，401 主路径照样摘。参考仓库佐证：new-api 的自动禁用默认状态码区间只有 `{401}`（`setting/operation_setting/status_code_ranges.go`），403 要靠额外的错误文案关键词匹配才禁——**关键词方案本项目不取**，那是把上游错误文案当契约，各家措辞不统一且会改版；new-api 需要它是因为它要服务不特定用户的不特定上游。
  - **只人工恢复，不做定时自动探测恢复**：自动探测恢复是把一份会过期的缓存放进请求路径，与本节「协议可达性探测只提示不进路由」是同一条立论。个人自用换把凭证是一分钟的事。
  - **摘光不设特例**：可用凭证归零即渠道不可用，请求按入口协议原生格式回错，管理端渠道列表红标。不做「最后一把不许自动摘」的保底——那把已经 401 了，留着只会让**每个**请求都吃一次确定性失效，把「凭证过期」伪装成「上游偶发抖动」；而全摘的失败是响亮且指向明确的。
- **凭证名**（v0.38）：每份凭证带一个人写的名字（渠道内唯一，不填默认 `凭证 N`），用于日志与用量归因。原先还附一条「网关不从凭证值派生任何显示字符」，v0.47 随「值可回读」一并撤销——值本身都摆出来了，掩码是不是派生字符已经不是问题。名字仍是**归因依据**：日志与用量按名字认凭证，别处不改用值来指代它。
- **渠道列表显示可用/停用凭证计数**（v0.38，原为「有无凭证」一个布尔）：0 可用时红标。摘光既然不设特例，「可用凭证归零」就是渠道从能用变不能用的唯一运行期路径，而列表页是唯一会被一眼扫过的地方；布尔在 3 把里坏了 2 把时显示的仍是「有凭证」，把最该被看见的劣化过程整个藏住。
- **拉上游模型列表：只做填表助手，不做路由依据**（v0.40）。管理端可以朝渠道声明的每个协议侧各拉一次 `GET {base_url}/v1/models`，结果**只摆进表单**（未纳管的一键加进来、模型只在部分协议侧列出时建议一个协议子集），人确认之后落库的是人的配置；**不落库、不参与路由、不做定时同步、不给「以上游为准」的同步动作**。
  - 做它的理由：手工核对「这个模型到底在哪一侧」要人去翻两边的控制台，而模型级协议子集（§2.3 v0.40）正需要这个信息。它不花钱也不发推理请求——`/v1/models` 是列表接口，判据是上游自己声明的列表，比「发空 `{}` 看状态码」还硬。两侧同形：OpenAI 与 Anthropic 都是 `GET /v1/models` 回 `{"data":[{"id":…}]}`，`openai` 与 `openai_responses` 共用同一次拉取。
  - 不做成路由依据的理由：**中转站的 `/v1/models` 撒谎是常态**——返回一份写死的大列表、含它实际并不支持的模型。这是本节「探测结果会过期，把一个可能撒谎的缓存放进路由路径是更坏的失败模式」那句话的实证，不是理论担忧。撒谎的列表进了表单最多让人多改两下，进了路由则是请求被静默送去一条死路。
  - 不按各家特判 URL：new-api 为 `/compatible-mode/v1/models`、`/api/paas/v4/models` 这些变体养了一张渠道类型表（`controller/channel_upstream_update.go`），那正是展开层 §6.1 明确不取的复杂度。拉不到就手工填。
- **协议可达性探测逐把凭证探**（v0.38）：结果按凭证分行显示，**含已停用的凭证**——恢复既然是纯人工的，「这把被摘的凭证现在还坏不坏」除了删掉重配就没有别的办法回答，逐把探正好是那个答案。它是人手点的按钮、不在请求路径上，所以「不把会过期的缓存放进路由」的约束不适用；结果仍不改状态、不落库、不进路由。

### 2.3 接入点与模型路由

路由的核心实体是**接入点**（沿用一套成熟生产网关的同名概念，语义简化）：

- **接入点**：客户端调用的入口，对外暴露一个模型名（客户端 `model` 字段填它）。每个接入点绑定 1..N 个**候选**，候选 = `（渠道纳管的模型，权重）`（v0.12：候选引用渠道已纳管的模型条目，不自由填字符串）。多候选时按权重加权随机分流；单候选即直连的退化情形，**不设 DIRECT/LOAD_BALANCE 二值配置**（个人版无需该复杂度）。权重置 0 即临时摘除候选。
- **渠道**：上游连接（**支持协议集** + base_url + 凭证池）+ 可用模型纳管，见 §2.2，不承担路由职责。**「供应商」不是独立实体**（v0.33）：一个渠道就对应一家上游的一次接入，同一家开两个账号或走两个中转仍是两个渠道；管理端的供应商图标分组是显示层的启发式（按 base_url host 与渠道名猜），不进数据模型。
- **模型映射/别名**：接入点对外模型名 → 候选所指渠道模型（上游模型名）的名字翻译，随候选绑定关系天然成立，不是独立实体。
- **对外模型名唯一寻址（v0.22，v0.32 修订）**：接入点对外模型名全网关唯一，客户端 `model` 字符串本身即确定路由入口。对外名撞名属「启动时即可判定必然跑不通」的配置，按 v0.21 通则启动即报。
- **纳管模型直连寻址（v0.32，推翻 v0.22 的「不设直连路径」）**：纳管模型除了经接入点暴露，还能被客户端**直接**调用，寻址用**限定名 `渠道名/纳管模型名`**（如 `bailian/qwen3-max`）。仍然**不做裸 modelId 寻址、不做「按模型名扫渠道」的兜底**——v0.22 封的是那条路，它的寻址不确定性没有变；限定名不属于它：渠道名全局唯一 × 渠道内模型名唯一 ⇒ 限定名天然唯一，「同名模型多渠道选谁」这个问题在限定名下构造不出来。
  - **渠道名不含 `/`（v0.34，补 v0.32 立论的漏）**：v0.32 说「渠道名唯一 × 渠道内模型名唯一 ⇒ 限定名天然唯一」，这一步只在渠道名不含 `/` 时成立——纳管模型名本身常带 `/`（`anthropic/claude-3` 这种），两边都放开的话渠道 `a` 的模型 `b/c` 与渠道 `a/b` 的模型 `c` 拼出同一个限定名。按 v0.21 通则在保存时校验、启动闸复查，不留到请求期猜。
  - **接入点优先**：接入点名恰好长成某个限定名时以接入点为准。接入点是显式配出来的对外契约，限定名是自动派生的。
  - 接入点因此从「唯一入口」退为**别名层**：它仍是配多候选、跨渠道分流、对外换名的地方，但「只想直接用某个上游模型」不必再为它建一条。
- **实现分期（v0.12 重排，v0.38 拆分）**：多候选加权分流、候选间故障转移的**实现**在 M4；**凭证池聚合（含 key 层内环）的实现前移至 M3**（v0.38）。口径与语义维持已决不变。M0~M2 配置校验强制**单候选、每渠道单凭证**（临时闸），失败不切换、直接按入口协议原生格式回错；M2 起该「不切换」之前先加一环同候选退避重试（v0.19），临时闸本身不放开。**M3 起临时闸只剩单候选那一半**（v0.38）——凭证那一半放开，启动闸由「恰好 1 份启用凭证」改判「≥1 份」。拆闸的依据同 v0.19（同候选退避重试从 M4 提前）：key 层内环整个嵌在候选 loop 内部，不依赖多候选分流，两条校验本就独立；现实压力是管理端的凭证 UI 正在成型，此时不改就得在 M4 把同一块代码改第二遍。**未停用接入点的候选必须真的可达**（其渠道、纳管模型、凭证均未停用）——「配置能过校验但请求时 503」不算合法状态，一律启动即报（v0.18）。**这是通则不是枚举（v0.21）**：凡启动时就能判定「这条配置必然跑不通」的，一律启动即报，不留到请求期；括号里那三项是当时遇到的具体形态，不是清单的全部（v0.21 新增：未停用渠道的 `base_url` 必须是带 host 的绝对 http/https 地址）。

**出站协议选择（v0.33，修订原「由候选所在渠道的协议决定」）**：命中渠道之后，本次请求走它支持协议集里的哪一个，规则是

0. **先与纳管模型自己声明的协议子集取交集（v0.40）**，交集就是这次真正的可选范围；模型没声明子集时交集即渠道全集。见下方「模型级协议子集」。
1. **入站协议优先——能透传就透传**。入站协议在集合里就用它，`/v1/responses` 进来打上游 `/v1/responses`。
2. 不在集合里才转换，目标按**固定优先级** `openai > openai_responses > anthropic` 取集合中第一个。不做成可配置：这是罕见分支，且 CC 是三者里字段最贫的，转过去的信息损失最可预测，6 条路径里也是 CC 侧最先落地、golden 样本最全。

立论是**上游协议的选择对用户可感知**：跨协议转换按 v0.10 丢弃 thinking，同一个模型走透传能留 reasoning、走转换就丢，所以这个选择不能是随机的、也不该要用户在模型名里自己标（协议因此彻底不出现在对外模型名里）。**复议触发条件**：若 Anthropic→Responses 路径日后能保住 reasoning（Responses 有 reasoning item 而 CC 没有），第 2 条的优先级顺序须重拍——那时 Anthropic 入站转 Responses 的保真度高于转 CC。

**模型级协议子集（v0.40）**：纳管模型可以声明「我只走这几个协议」，取值是渠道支持协议集的子集，**不声明（空）即继承渠道全集**——绝大多数模型都该是空的。填的动机是渠道级的协议集回答不了「渠道会说 anthropic」与「渠道下**这个**模型在 `/v1/messages` 上存在」的差别：聚合型中转在同一前缀下同时提供两套子路径是成立的（§2.2），但它转的 `gpt-4o` 未必在 Anthropic 那一侧列出。此前的表现是渠道级探测全通、请求照样 404，且看不出是配置问题。四条边界：

- **不校验它是不是渠道集的子集，存原样、路由时取交集**。渠道协议集缩小时级联清理这一列，等于拿「配置任何时刻自洽」换「你改渠道时我替你删配置」，而删掉的填法回不来；取交集则是渠道把协议勾回来，这一行自动重新生效。管理端把可选项限在渠道集内，同时**照实显示**渠道已不支持的存量值（它此刻正让这个模型不可用，藏起来只会让人对着一个「看上去哪都没问题」的配置查 503）。
- **交集为空 = 这个模型当下用不了**，与「渠道停用」「可用凭证归零」同一档，按入口协议原生格式回 503；不是数据损坏、不报 500，也不进启动闸——直连路径本就不进启动闸（v0.32），而接入点路径上这是运行期才成立的状态。
- **`GET /v1/models` 两半边都不列交集为空的名字**（v0.41）。v0.32 ③「列出来的必须调得通」当初只落在直连那半边，理由是「直连不进启动闸，启动闸兜不住它」；而交集为空按上一条**也不进启动闸**，于是接入点那半边同样兜不住——同一条理由现在覆盖两边。接入点按「**有没有一个候选活着**」判（不是「有没有一个候选死了」）：M4 放开多候选后，一个死候选不该把整个接入点从清单上抹掉。
- **这不是「能力探测」，也没有推翻下面那条**。它是**人工配置**手段，正是下面「配置人自己保证」这句话缺的那个表达方式：此前配置人知道某个模型只走 openai，却没有地方把它写下来。
- **M4 多候选放开时，交集为空的候选必须在加权抽取之前排除**。只有一个候选时「抽完再判」与「先滤后抽」等价，多候选下则不然——死候选会白占一份权重，把请求判死在一个本来有兄弟候选能接的接入点上。

候选可跨协议混布（如接入点 `claude-sonnet` → Anthropic 官方 70 + 某 CC 兼容中转 30）。**多候选放开（M4）时，入站协议同样参与选候选**（v0.33 定口径、不提前实现）：能透传的候选优先，权重降级为「**同透传档内**的权重」。理由同上——在候选层随机挑一个会丢 thinking 的候选，和在协议层随机挑是同一个错误，两层必须同一条规则。

不做通配符匹配、不做模型自动发现、不做候选间能力等同校验（配置人自己保证）。**「不做模型自动发现」指的是不自动纳管、不拿上游列表当路由依据**（v0.40 澄清）——管理端可以拉一次上游 `/v1/models` 摆进表单让人挑（§2.2），那是填表助手，落库的仍是人确认过的配置。**能力探测（工具调用支持、思考模式支持）不做（v0.33）**，与协议可达性探测（§2.2，做，仅提示）分开看：①它就是「能力等同校验」的自动化版本，做它得先推翻本条；②探不准且不可证伪——判定「支持工具调用」要发一个真带 `tools` 的请求看模型调不调，而它不调不等于不支持，`reasoning_effort` 被上游静默忽略与模型这次不想想在响应上也分不出来；③没有消费者——网关不按能力拦请求（透传保真优先），探出来的位只能在管理端画个图标。真需要能力信息时（如 M4 按「工具调用失败过」排除候选），走**从 `call_logs` 学**而不是主动探测：观测数据不过期，反映的是真实行为不是自称。

### 2.4 API Key

- 生命周期：创建 / 启用 / 停用 / 删除。**不做过期时间**（v0.27 收敛 C6）：个人自用，停用即可，不值得为它在表、鉴权、界面三处各加一道。
- Key 在哪个设备/工具上用是用户自己的事，网关不做设备绑定。
- 存储：hash 落库，明文只在创建时展示一次；统一前缀 `sk-ptg-`（v0.16 定 `sk-aig-`，v0.42 随改名换掉）便于日志排查。
- 每把 key 可限定**可访问的模型**（`allowed_models`，`*` 即不限）。M1 只建列不校验，M3 管理端能配的同时启用转发端校验（v0.28），越权回 403。**白名单逐项精确匹配客户端填的 `model` 字符串，接入点名与纳管模型限定名两种都能写（v0.32）**——两种名都能路由，白名单只管一种就等于给受限 key 留了条绕过去的路。v0.28 之前那条「配 key 的人看不到纳管模型」随直连口径一并作废。
- 不做配额、不做计费、不做按 Key 限流（v1）。

### 2.5 用量记录

每请求一行流水，SQLite 落库：时间、key、入站协议、模型别名、渠道、**上游凭证名**（v0.38）、上游模型、输入/输出 token（**输入是毛值**，v0.71）、**思考 token**（v0.66，可空）、是否流式、首字延迟、**排队等待**（v0.52）、总耗时、HTTP 状态、错误摘要、**上游错误原文**（v0.53）、**上游 request-id**（v0.56）。不做聚合报表，要看直接 SQL / 管理端简单列表。

**思考 token 单成一列，且这一列必须可空（v0.66 定，[#97](https://github.com/SimonGino/portage-legacy/issues/97)）**：流水加 `reasoning_tokens`，canonical 也加一格，两处都是**输出 token 的明细而非另一笔加数**——四份真实转录里 `total` 恒等于 `input + output`，思考一次都没进这个加法（**不存在重复计费**，这是本条最要紧的事实）。认这一格的理由是 v0.65 的「已发生的成本不得静默吞没」：实弹上工具轮 10 对正文轮 157，差一个量级，不认则这两次调用在流水里的成本结构看起来一模一样。

**三档必须分得开**：正数 = 这次思考花了这么多；**0 = 上游报了、这次没思考**；**NULL = 上游根本不报这个数**。后两者不是一回事——~~Anthropic 协议里没有这一格（三家参考实现的旁证：litellm 对 Anthropic 是本地 `token_counter` 重新数的，上游要是报了它不会自己数）~~，**Anthropic 其实有这一格，v0.79 由自己的字节订正**：开了思考的响应在 `usage.output_tokens_details.thinking_tokens` 上报数（两份新转录 249 / 310，且都小于同一份 `output_tokens`，仍是明细不是加数）——原文那条旁证只是参考实现没读这一格，不是协议没有。这不撤销 NULL 那一档：**没开思考的 Anthropic 响应连 `output_tokens_details` 这个对象都不发**（本库六份非思考 anthropic 转录逐字节核过），所以 A 渠道照旧要能出 NULL；CC 上游挂非推理模型时整个 `completion_tokens_details` 也不发；抹成 0 会让 Anthropic 渠道与 v0.66 之前的全部历史行显示成**确凿的零思考成本**，那正是本条要防的静默。**缺的那侧不做本地估算补齐**（litellm 那种做法）：估出来的数与上游报的数不同源，落进同一列就再也分不出哪个是真的，理由同 v0.65 ②「不折算数字」。

**记的永远是上游报的数，与出向合成与否无关**：流水答「这次调用花了多少」，合成是给客户端看的呈现，两件事。展示只动**调用记录**一页（有数才露一行「思考 N」，同缓存读写那条的成例）；概览与排行不动——思考已经在输出 token 里面，单列会被读成额外一笔。

**上游 request-id 落流水（v0.56）**：上游响应头里的 `request-id` 除了原样回传客户端，另存一份进流水——报障与对账要的就是这个 id（官方文档明写报障时附它），只在客户端那边有的话，事后自己查还得去翻客户端日志。头名以官方拼写 `request-id` 为准、`x-request-id` 兜底（中转与自建上游常用这个名），两个都在时取官方那个。它不是凭证材料，进日志无碍。

**取值顺序加第三档「读错误响应体」（v0.74 定，#37）**：`request-id`（官方头）→ **错误响应体里的 `request_id`** → `x-request-id`（中转/自建常用名）。①**新档插在中间不是末尾**：前两档都是 Anthropic 自己写的，`x-request-id` 是中间层给自己编的号——v0.56 那句「两个都在时取官方那个」的立论直接管这里，实测的形状恰恰是「头里是中转的 uuid、体里是官方的 `req_…`」，插在末尾等于永远取不到官方那个。②**只有失败行拿得到**：实测（2026-08-15，五份真实响应）`request_id` 只出现在 Anthropic 的错误信封里，成功响应的体（流式与非流式都是）**一个都没有**。所以这一档修的是**报障对账**那一半——恰好是这个 id 最常被用到的场景——成功行的用量对账仍然只能靠头，头被裁了就是没有。③**破例的边界**：透传路径不做 decode→encode 这条约定不因此松动——失败行的响应体**本来就要读**（`error_detail` 截 2KB 存原文，v0.53），这一档只是在那份已经读进来的字节上多解一个键，不新增一次读、不重序列化、不改写回给客户端的字节。成功行一个字节都不多读。④解不出来（不是 JSON、没有这个键、流式错误帧的形状未知——本库无样本）就当没有，落空串，不失败、不告警。

**这个 id 要在管理端露出来，落点是「详情」那一层（v0.67 定，[#81](https://github.com/SimonGino/portage-legacy/issues/81)）**：v0.56 只把它落了库，管理端一个地方都没露，要对账只能翻网关日志或直接 `sqlite3` 查表——而它落库的**全部理由**就是「事后不用翻日志就能查到」，不给查询面这一列等于白加。落点选「详情」而不是新起一列或压在时间列下面：它二十几个字符，占列会把表撑出卡片，而这个 id 是「要用的时候才去找」的东西，不是每行都要扫的。**由此改掉一条既有判据**——「详情」此前只对 `status >= 400` 的行出现（它是为 `error_detail` 建的，那一列只有失败行有值），而 request-id **成功行也有**且成功行的 id 一样有用（用量对不上、想问上游这次到底计了多少）。判据因此从「这一行失败了吗」放宽成「**这一行有没有细节可看**」，这也正是这一层本来的语义，`error_detail` 只是它此前唯一的内容。**框里每一段各带各的判据**：上游原文仍只在失败行摆（它那几句兜底文案对着一次 200 全是假话）。**必须可复制**：对账要把这个串粘给上游，手抄 `req_018Ee…` 必错。空串一档吃掉三种情况（没走到上游、上游没回这个头、v0.56 之前的老流水），一律显示为缺值符号，不单独提示——它们在对账上是同一件事：没有可用的 id。**不做按 request-id 的筛选/搜索**：它逐次唯一，筛出来永远只有一行，而人拿到 id 的场景是「从上游那边往回查」，不是「在网关里搜」。

**错误的两层（v0.53）**：`error` 列是网关自己的**固定词表**（可枚举、可聚合），`error_detail` 是上游说的那段话（不可控文本，截前 2KB，只在失败时存）。分两列而不是一列：词表要能 group by，原文要能读；混一列则两头都不成立。原文**只走管理端**——转发路径回给客户端的仍是固定词表与 `error.message` 一句（§2.7 的不外泄约束不变）。

**这份词表就是这十个词（v0.70）**：`upstream_error`、`stream_aborted`、`unauthorized`、`rejected`、`queue_full`、`queue_timeout`、`queue_abandoned`（并发闸三个，v0.52）、`compaction_unsupported`（v0.54）、`model_not_allowed`（key 白名单拦下）、`rate_limited`（网关限流拦下）。**`ok` 不是第十一个词**，它是判据里的哨兵——收场词不等于 `ok` 才写 error 列，成功行这一列留空，`ok` 永远不进库、也不该出现在任何筛选选项里。**空值一律给空串**：库里这一列可空（空 = 这行没有错误词），接口层对外照原样给空串不转 null，前端只判空串——同 v0.67 ⑤给上游 request-id 定的规矩，同一个前端里两列不该有两套空值约定。

**收场词表跨路径对齐（v0.63）**：同一件事在透传与转换两条路径上必须落同一个词。第一个具名实例是**断流**——客户端中途断开（Ctrl-C、超时）这类读上游读断，透传路径一直记 `stream_aborted`，转换路径此前记的是干净的 `200/ok`（读断在那条路上是带内往下传的，调用方从返回值里看不出来）。只认**传输失败**：上游在流里回的错误对象不算，那个透传路径同样记 ok，硬要在转换这边降级只会让两条路径换个方向再分叉一次。原文按 v0.53 落 `error_detail`（脱敏后的错误本身），不加列、不改回显契约。

**流水的输入 token 是毛值，归一发生在落流水那一步（v0.71）**：毛值（= 上游净输入 + 缓存读 + 缓存写）此前只定在 canonical 那一格（v0.54 ③），而流水从来不经过它——落库取的是各协议计数器留下的上游原样数字，计数器**按渠道协议选**，于是 Anthropic 渠道的行存净值、CC / Responses 渠道的行存毛值，而概览与排行**无条件跨协议求和**，两种单位正在相加，缓存命中重的 Claude 渠道被系统性低估。因此**入库前按渠道协议把 Anthropic 行的缓存两项加回输入 token**，与 canonical 同一条规则、同一个毛值定义。计数器留的那份上游原样数字不变，它的身份是排障线索——不归一的是那个中间物，不是流水这一列。

**用量聚合的三个维度（v0.53 补第三个）**：按模型、按**网关 API Key**、按**上游凭证**。后两个是两件事——一个是「我发出去的这把 key 用了多少」，一个是「上游那个号跑了多少」——展示上一律写全称，只写「按凭证」两边都像。日志列表的筛选（模型 / key / 只看失败）与翻页在服务端做，不在已取回的一页里过滤。翻页给**页码**且**能直接跳**（v0.61），页与页之间看到的是同一批数据——进页那一刻定住看哪一批，其后新写进来的流水要按「刷新」才进来。

**「没解析到模型名」单成一档，且这一档可筛（v0.64）**：401 鉴权失败、请求体不是合法 JSON、缺 `model` 字段这几条路径都在解析出模型名之前就返回了，流水里模型那一列是空串。这些行**不丢**（丢了模型维度的总次数与概览的合计就对不上，理由同 v0.38 对空凭证名的处理），但也不能让空串原样进模型维度——模型筛选里空串正是「全部模型」的取值，两行会同时显示成选中。给它一个具名档位 `(未记录模型)`，与按 key 维度的 `(未鉴权)`、按凭证维度的 `(未记录凭证)` / `(未走到上游)` 同一种取名法。**与那几个不同的是它还接受为筛选输入**：聚合里露出来的每一档都得点得进去，点了没反应的选项比没有这个选项更糟。**代价明说**——这个名字因此同时是显示 label 和查询参数值，客户端真请求一个叫 `(未记录模型)` 的模型就会撞上它，届时**哨兵优先**，那个模型筛不出来也会被并进这一档的聚合行。判为可接受：单人网关，模型名是自己配的，全角括号是刻意选的；真撞上再改成 label 与查询值分离的双字段形状，那要三个维度一起动。

**统计窗口 = N 个自然日·本地时区（v0.55）**：「近 7 天」指今天往前数 7 个自然日（今天算一天），不是滚动的 7×24 小时；`created_at` 存 UTC，分桶与窗口边界都按运行机器的本地时区算。这条此前是隐性的（滚动窗口），加了按天的柱状图之后它会直接显示在横轴上——滚动窗口的最老那根只覆盖大半天，每次看都矮一截，而那是窗口切得巧、不是那天真的少。图与汇总表共用同一个窗口，否则同一张卡上两个数对不上。

**用量页做排行的形态、不做排行榜的那三块（v0.55 立，v0.58 收窄）**：PO 拿 OpenRouter/ArcReel 的排行榜页作参照，v0.55 裁定不照搬——热门模型榜、市场份额、上升/下降趋势这三块要的是**分母或上一周期**，而这是单人网关：模型是自己配的那七八个，「热门」问的是别人在用什么；参照图里 ↑8500% 那种数字在这个量级上 5 次调用就能造出来（DESIGN §6「材料撑不起的结论不用图表制造」）。另有两处硬约束：市场份额按厂商分色，而库里没有厂商字段，管理端的图标是从模型名猜的，拿猜出来的东西画占比等于把猜测画成数据；环比与排名变化要查上一周期，现有聚合只有单窗口。**v0.58 收窄的是「不照搬」的范围**：PO 再拿 new-api 模型广场与 OpenRouter rankings 作参照，裁定汇总表改成排行**形态**（名次 + 图标 + 名字 + 一个主指标 + 占比）——形态不需要分母也不需要上一周期，名次是把自己这段时间的行按 token 排一遍，占比的分母就是同一张卡上的合计。**那三块仍不做，两处硬约束原样有效**：要上必须先解决库里没有厂商字段、聚合只有单窗口这两件事，届时另裁。同批取的还有那根时间轴：图按天，回答「什么时候烧的」——「谁在烧」由排行逐行回答，两者不重复。

**观测拆成三页：概览 / 调用记录 / 排行（v0.60）**：原先这三件事挤在导航那一项「用量」下（v0.55 ④曾裁定「导航项仍叫用量、卡片不再与页面同名」），PO 2026-08-13 裁定拆开，v0.55 ④那半作废。三页各答一问，问题不同、时间尺度也不同：**概览**答「这段时间烧了多少、什么时候烧的」（指标条 + 按天柱状图），**调用记录**答「刚才那几次怎么样」（逐行流水，排障用，即时），**排行**答「谁在烧」（按 token 排的名次 + 占比，回头看）。一页一问的直接好处是**同一份数据不再在两处各说一遍**（DESIGN §6）：合计只在概览摆全（调用 / 失败 / token），排行页只留 token 合计那一个数，因为它是每行占比的分母，没有它「57.9%」没有出处。统计窗口各页自己持有：调用记录页干脆没有窗口（页码能一直往回翻，天数在那里没有意义，只有模型下拉的选项要一个窗口，取最宽的 30 天）。导航因此从四项变六项，前三项是「配的」、后三项是「看的」。**v0.75 去掉概览**：导航改五项（模型 · API Key · 调用记录 · 接入点 · 排行），`/overview` 与 `/usage` 重定向到 `/rankings`；侧栏改做（推翻 DESIGN v0.5/v0.17「侧栏不做」），账号钉左栏底。

**上游凭证归因（v0.38）**：流水记的是**本次真正发出请求的那份凭证**（换过凭证时记最后一份，失败亦然），一次调用仍只有一行——不记完整尝试轨迹。轨迹的主要价值（谁被摘了、为什么）已被凭证自身的停用原因与停用时刻覆盖；而把轨迹塞进流水会让它从扁平表变成半结构化，用量统计每次都得先解结构。真需要轨迹时再加，加的是列不是改表义。展示面两处：日志页加「上游凭证」列（单次归属，排障用），用量页加**按凭证聚合**的视图（「这个号跑了多少、还剩多少」是聚合问题，只给逐行表等于把统计留给人肉眼做）。

### 2.6 高级字段透传（对 harness 体验关键）

- Anthropic `cache_control`（prompt caching）：**必须透传**，否则 Claude Code 成本数倍上涨。
- thinking / reasoning 内容块（**v0.62 复议，推翻 v0.10**；同协议透传保留不变）。v0.10 把「出向合成」与「回带风险」绑成一条论证，复议把它拆成两半分别裁：
  - **出向（上游 → 客户端）：合成，六条转换路径对称**（原文「四条」，v0.73 补上 CC↔R 两条）。CC 的 `reasoning_content` / Responses 的 reasoning item → Anthropic `thinking` 块；反向 Anthropic 的 thinking → CC 的 `reasoning_content` / Responses 的 reasoning item；CC 与 Responses 之间同域互转。**流式与非流式都做**（共用同一台状态机，不做成两处判定）。
  - **`signature` 一律省略**：不发字段、不发空串、不伪造。空串比省略更糟——Anthropic 明确拒收空/缺失 signature 的 thinking 块，空串是把「没有」伪装成「有」。伪造仍是禁区：口径是「上游给了绕过校验的口子才造，没给就不造」，Anthropic 没给（对照 new-api 对 Gemini 造、对 Anthropic 不造）。
  - **回带（客户端 → 上游）：维持一律丢弃**（现状即如此），并**补齐丢弃登记**（`anthropic` 那侧今天连 drop 都不登记）。不做 provenance 嗅探：它的收益只在「同会话前后两轮路由到同一个 Anthropic 上游」这一格兑现，而本网关是无状态选路、渠道随时可换；判错的代价是下一轮 400 砖死会话，判对的收益只是省一次重新思考。这一裁决使出向合成的块**永远不会被送回上游**，闭环自洽。
  - **Responses 出向那一格：口径已定「要合成」，样本已采**（原文「实现待样本」，#93 兑现）。它此前丢弃的理由不是本条口径，而是缺真实转录钉 reasoning item 的生命周期（那时手上三份转录里只有 `encrypted_content`、一条 delta 都没有）——那是排期问题，不是口径问题。#93 采到的 `responses-stream-reasoning-turn1` 把 `reasoning_summary_part.added` → `text.delta` → `text.done` → `part.done` 整条生命周期录全了；转录随该票的分支入库，合并后这一格只剩实现。
  - **出向不加任何闸：客户端的显示偏好不构成不合成的理由**（v0.65 补）。立论是一条独立口径——**已发生的成本不得静默吞没**：上游已经生成并计过费的思考内容，网关必须让它对用户可见。Claude Code 五份入站样本都带 `thinking.display:"omitted"`，但那是 Claude Opus 4.7+ 的**默认值**（`"summarized"` 才是 4.6 的默认），不是用户表态；且它描述的是「让 Anthropic 上游别生成摘要」省下的那笔钱，跨到 CC 上游后那笔钱根本不存在——`reasoning_content` 已经生成、已经在流里、已经计费，此时丢弃不省一分钱，只把本节起因里那几秒空白原样还给客户端。因此 `thinking.display` / `reasoning.summary` **只是请求侧参数**，按下条登记后丢弃，**不作用于响应侧**。
  - **无 signature 的显示行为已实测**（#94，原「待实测」条兑现）：Claude Code 2.1.232 正常接收并显示，无报错无告警；空串与省略在客户端侧逐字节同结果——故上面「不发空串」的依据**只有上游侧**，不要扩大到客户端。实测同时抬高了回带那条的分量：客户端会把块**原样回带**并把缺失的 signature 自己补成 `""`，正是 Anthropic 拒收的形态，于是「回带一律丢」不是保守选项，而是链路自洽的唯一前提（合成而不丢，第二轮必 400）。
- **请求侧的思考参数：只映「思考多少」这一维，同域直传**（v0.65 定，#95）。思考档位由此成为跨协议的一等概念，不再是各协议的 vendor 字段（落点见展开层）。
  - **三协议在这一维本来同域**：Anthropic `output_config.effort`、CC `reasoning_effort`、Responses `reasoning.effort`，取值都是 `low|medium|high` 一路的字符串（Anthropic 侧的官方值域实测为**五档** `low|medium|high|xhigh|max`，v0.72 由 400 的报错文案逐字取回）。九份真实入站样本里**一个数字预算都没有**——Anthropic 自己已把预算从 `thinking.budget_tokens` 挪到 `output_config.effort`，`thinking` 只剩「开不开 / 展不展示」两维，与上面出向那条正好是同一个正交拆分。
  - **不做数字折算**。参考实现的档位表互相矛盾（new-api `high=4096`，CLIProxyAPI `high=24576`，差六倍），而这个数直接决定成本与延迟、没有客观依据。**直传是无损的，折算是编的**。客户端真发数字预算（Qwen 一路的 `thinking_budget`）时登记后丢弃，不折算。
  - **六条路径全放开，载体统一取 `output_config.effort`**（v0.72 定四条、v0.73 补 CC↔R 两条，推翻本条原文「只放开 A→CC 与 A→R」）。原文之所以只放一半，是因为不知道 Anthropic 侧该写新旧哪个载体、而判断它需要模型能力表；#37 实测（2026-08-14）把这个前提消掉了：`output_config.effort` 对 claude-sonnet-5 **合法、被校验、且真的生效**（`low` 10 个思考 token 对 `high` 310 个），并且**单发就能开思考**（不带 `thinking` 也吐 thinking 块，424 个思考 token）——所以既不需要认模型选载体，也不需要额外合成 `thinking:{type:adaptive}`（那才会撞上下面「不替客户端开思考」）。老式 `thinking:{type:enabled,budget_tokens}` 这个载体本网关**一次都不写**。**残留的未知只剩一格**：非 adaptive 的老 Anthropic 模型收到 `output_config` 会不会 400——本机没有纳管这类模型，无量具；判为可接受，理由与下面「域外值不钳」同一条：真撞上是一个看得见的 400，不是静默降档，而为一个自己不用的模型引进模型能力表是拿主线换支线。以下原文留痕，记着这条口径当初为什么是半开的——
  
    > 这两条两端同域，字符串直传、不需要认模型。**CC→A / R→A 维持丢弃 + 登记**：Anthropic 侧有新旧两个载体（`output_config.effort` 配 `thinking:{type:adaptive}`，与老式 `thinking:{type:enabled,budget_tokens}`），选哪个取决于目标模型，而三家参考实现在这一格全靠模型能力表（new-api 认模型名前缀、CLIProxyAPI 有 per-model registry、litellm 有 `_is_adaptive_thinking_model`）——那是本网关**架构上刻意没有**的东西（无状态选路），为一个字段引进它是拿主线换支线。备选「赌 `output_config` 对所有 Anthropic 模型都合法」被否：不认识的顶层键会被严格中转整体拒收，那正是 CC 出口丢弃 vendor 字段时防的坑，不该换个方向再踩一次。「`output_config.effort` 对非 adaptive 模型合不合法」挂 §5 / #37 实测，通过后再放开这两条。
  - **网关不替客户端开思考**：客户端没发思考参数就一个字不加。不按模型默认开，也不做「默认关的配置项」——那会立刻引出「配置说开、客户端说关」的优先级债，为一个还没人要的能力提前欠账。
  - **域外值不钳**：入站 effort 是出口侧未必认识的档（如 Anthropic 的 `max`）时原值直传。钳需要知道上游认哪几档，又回到模型能力表；而直传时上游若拒是一个看得见的 400，钳则是**静默降档**，与「不折算」反对的是同一件事。
  - **登记单立一档**：思考参数里没映过去的维（`thinking.display`、`reasoning.summary`、数字预算、CC→A / R→A 方向的整条 effort）不并进 `vendor_request`。理由同当初把 `metadata` 从 `vendor_request` 拆出来——effort 映走了、display 没映，混在一个登记项里，日志上看不出「我的 effort 到底传没传」。
- 多模态输入**分两类办**（v0.39 收敛，原文「同协议透传支持；跨协议转换 v1 不做」自 v0.37 起已作废，那次漏改）：
  - **图片：跨协议真做转换**（v0.37）。三协议都原生支持，丢弃是网关自造的能力退化。Anthropic 的 `image.source` 有**三种**形态（官方 vision 文档 2026-08-11 核）：`base64{media_type,data}` / `url{url}` / `file{file_id}`（后者需 `anthropic-beta: files-api-2025-04-14`）。
    - **远程 URL 形态要留住**：网关原样转发 `source.type=url`，**不代客户端下载**（下载是另一个量级的事：出网、超时、体积、SSRF，全在 v1 范围外）。
    - **`file_id` 形态登记后丢弃**（v0.39）：canonical 留字段装它，但**跨协议一律丢并单独登记**，不混进 `DropVendorContent`。理由是它**天然不可搬运**——file_id 是上游作用域的句柄，Anthropic Files API 发的 id 拿到 OpenAI 上游什么都不是（反之亦然），能搬运只有「下载再重传」一条路，而那条路已被上一条排除。留字段不是为了转换，是为了让丢弃日志说得出「丢的是一张 file_id 引用的图」，而不是一句「有个不认识的块」。
    - **精度提示 `detail` 跟着图一起转，不是丢弃项**（v0.78）。CC 与 Responses 都原生有这一格（`low`/`high`/`auto`，影响上游的切图与计费），能搬就搬——同「真做转换」的立论：两边都支持而网关不搬，是网关自造的能力退化。**取值原样转发**（含 `auto`），不设白名单、不替客户端解释「auto 等于没指定」，同上一条。**只有 Anthropic 方向是丢弃项**（它没有对等的一格），单独登记 `image_detail`，理由同 `file_id` 那条：丢的是什么要说得出口。
    - **格式不设白名单，原样转发，上游不认就让它 400**（v0.77）。Anthropic 只认 jpeg / png / gif / webp，CC 的 `image_url` 什么 data URI 都收，`image/svg+xml` 转过去必被 400——这是看得见的上游错误，不是网关该拦、该丢、该转码的事。与 §2.6「域外值不钳」同一条：钳或丢是静默削能力，网关自造 400 是另开错误面。不转码（opencodex 用 Bun.Image 把名单外压成 JPEG），那和「不代客户端下载」同一量级，不进 v1。
  - **音频（`input_audio`）与文件类：维持登记后丢弃**（v0.39）。「丢得有声音」已由 #32 的 `DropVendorContent` 登记兑现，与 thinking 那条同待遇。
    - **待裁**：v0.39 原话是「Anthropic 侧没有对等形态」，这句**对 PDF 不成立**——Anthropic 有独立的 `document` 块收 PDF 与 text/plain（`{"type":"document","source":{"type":"base64","media_type":"application/pdf",…}}`），其余文件类型走 `container_upload`；litellm 就是按 `media_type == "application/pdf"` 分流的（`prompt_templates/factory.py:2002`）。所以「文件类」不是铁板一块：PDF 有对等形态、可以真做转换，其余没有。是否把 PDF 单独提出来按图片同办，没定。

  > 参考实现的反面教材（sub2api `apicompat/`，2026-08-11 查证）：它的 `AnthropicImageSource` 没有 URL 字段、`Type` 写死 `base64`，非 data URI 的图到 Anthropic 方向**静默丢弃**——不下载、不报错、不记日志；`input_audio` / `document` / `file_id` 同理，所有内容 switch 都没有 `default`。方向（宁可丢内容不让整个请求转换失败）与本项目一致，但**丢得没有声音**这点本项目已判过不行。
- 响应 id：**跨协议转换时原样透传上游的 id，不改写成目标协议的形态**（v0.31 定）。上游一个 id 都不发时才由网关补一个，补的值带目标协议的原生前缀，与透传来的一眼可分。

### 2.7 部署与安全

- 测试环境 Mac mini，生产环境 Linux 公网 VPS。
- 公网暴露前提下的必做项：TLS 由反向代理承担（**nginx 为主、Caddy 备用，v0.29 定**）；全局限流兜底（防 key 泄露刷爆上游账单）；上游真实 key 仅存服务端 DB，错误信息中严禁回显上游 key 与 base_url；管理端与转发端口分离或路径隔离 + 管理员认证。
- 全局限流（v0.15 已决）：单个全局令牌桶，10 QPS / 突发 20，超限回 429（带 Retry-After）；配置可调（`rate_limit_qps` 写 0 即关闭），M3 已落地。不分 key/IP 维度（v1）——目的仅是 key 泄露/被扫时钳制上游账单损失。与渠道并发上限（§2.2 v0.49）并存不合并：桶限入口速率保护网关自身，闸限出口存量保护上游。
- 管理端认证（v0.14 已决）：单管理员；密码首启由 `config.yaml` `admin_password` 初始化、登录后可改（改后配置项失效）；session = 服务端内存 + HttpOnly cookie，重启失效重登，不做 remember-me / 多设备 / 2FA；管理 API（认 session）与转发 API（认 api_keys）鉴权彻底分离，互不可用。
- 管理端隔离形态（v0.28 定）：**同端口不同路径**——管理面全在 `/admin` 下（页面 + `/admin/api/*`），转发面在 `/v1`。不另起端口：单二进制单进程，两个监听只是多一份配置和一次「忘了发布哪个端口」的机会，隔离靠的是两套互不可用的凭证而不是端口号。公网暴露时由反代只放行 `/v1`、`/admin` 走内网或额外认证。
- 管理密码的初始化来源（v0.28 定）：`config.yaml` 的 `admin_password` 或环境变量 `PORTAGE_ADMIN_PASSWORD`（env 优先）。加 env 是为容器——镜像里那份配置是烤进去的，密码写在里面等于写进镜像层历史。**两者都只用于初始化**，库里已有密码就一概不生效。
- 反向代理选型（v0.29 定）：**nginx 为主，Caddy 列为备用**。依据是运维现实——目标机器上本来就跑着 nginx（443 只能有一个主人），且我手上另一套网关用的也是同一套配置习惯，认知成本为零。代价是 nginx 的默认值对 SSE 不友好——`proxy_read_timeout 60s` 会静默掐断长流，`proxy_buffering on` 叠上父配置的 gzip 会把整条流攒住，`client_max_body_size 1m` 会 413——都得显式改，且漏配不报错。配置样例 `deploy/nginx.conf.example` 与实测记录见展开层 §11.3。Caddy 在这一点上零配置就对，若将来换一台干净机器可以重新考虑。
- SSE 响应带 `X-Accel-Buffering: no`（v0.30 定）：网关主动发，让前面那份未必由我们维护的 nginx 对本次响应关掉缓冲。这是透传路径上唯一一处「上游没发、我们加上」的响应头，非流式不加。实现见展开层 §7.3。
- 上游凭证**可回读**（v0.47 推翻 v0.28 的「只写不回读」）：凭证池那一个接口发全串，页面默认掩码、给「显示」与「复制」。PO 的立论是「不然没法直观地表达这是哪一把」，而值本来就是明文存库的，回读没有降低任何既有强度。仍然守住的两条：①**只有凭证池那一个接口发它**，渠道列表、接入点、流水、错误回显一律不带（回归测试 `TestAdminReturnsCredentialOnlyFromThePool` 盯着）；②**转发链路吐给客户端的东西里永远没有上游 key 与 base_url**——那是另一条纪律，跟管理员登录后看自己的配置是两码事。**写入形态自 v0.38 由「整把替换」改为逐条 CRUD**（加一条 / 删一条 / 停用 / 启用），另给一个语义为**追加**的批量粘贴入口。整把替换在多凭证下讲不清楚：覆盖会连带清掉已停用的凭证，而那是 401 摘除的现场，是「这把为什么不转了」的唯一记录（v0.47 让值可回读之后，原立论里「页面上对不齐」那半条不再成立，这半条仍然成立且是决定性的）。列表显示名字、值（默认掩码）、状态、创建时间、停用原因与时刻。

### 2.8 技术栈

- 后端：Go + Gin；SQLite（GORM 或 database/sql 均可，展开层定）。
- 前端：React 管理端（`web/` 子目录），构建产物 embed 进单二进制（new-api 同款做法）。
- 配置：启动引导只用最小配置（端口、DB 路径、管理员初始密码）；渠道、模型映射、key 全在 DB 由管理端维护。

## 3. 边界与非目标

- 不做：多用户/租户、计费与充值、渠道分组（权重负载均衡要做，见 §2.3；new-api 式的用户等级×渠道分组体系不做）、兑换码、通知、评测、ES 日志、模型训练相关一切。
- embeddings / rerank 只做透传，不做跨协议转换。
- 图像生成、audio 端点：v1 不做。
- 渠道级熔断、自动探活恢复：不做（v0.51 正面审视后重申 v0.38 的无熔断范式，立论见 §2.2「拥塞期行为」条目）。上游拥塞期的保护由并发闸 + 有界排队（v0.49/v0.50）承担。
- 消费上游指标（读 SGLang Prometheus 等做机制或展示）：不做——机制半边 v0.51 封（会过期的缓存进路由），展示半边 v0.52 封（网关保持自包含，上游侧自有监控）。
- 重试与故障转移（v0.9 已决，v0.19 修订「无同候选重试」一条）：候选间故障转移——429/5xx/网络错误/连接超时且未向 client 写出首字节时，剔除失败候选，对剩余 weight>0 未试过的候选重新归一化权重再抽；耗尽即回最后一次上游错误；其余 4xx 不切换直接回错。采用 A-14 D3 范式：不探测、不记忆、不摘除，跨请求无熔断状态。**同候选退避重试（v0.19 恢复，实现落 M2）**——429/5xx/网络错误且未写首字节时，先对同一候选同一 key 按退避重试，耗尽再走上面的候选间转移。这推翻 v0.9「无同候选重试，重试留给 harness」：该决策的依据是 harness 会自行退避，而 M0 验收实测（#6）证伪了一半——Codex 0.144.1 对 5xx 退避、对 429 一次即弃，上游限流时无人自愈。流式已开始输出后一律不重试不转移。**key 层内环（v0.11，v0.38 修订，实现落 M3）**：命中候选后，429/401/403 且未写首字节 → 先在渠道内换未试过的启用凭证重试（**只有 401 同时摘除该凭证**，403 换而不摘，见 §2.2）；5xx/网络错误 → 不换凭证，直接切候选；渠道内凭证耗尽 → 该候选判失败，走候选间转移。**429 不做凭证冷却**（v0.38）：冷却是新引入的时间态状态，而 429 不像 401 那样是确定性的；撞上的代价已被「同一次请求内换过去就成功」吸收，客户端感知不到。真被高频限流打疼了再加，加的是内存里一个 map，不动数据模型。

**尝试次数预算分两层（v0.38）**：内层每份凭证各自 `retry.max_retries`（默认 2），外层一次请求一个全局尝试上限 `retry.max_attempts`（默认 6）封顶。不取「不设全局上限」——最坏耗时会随凭证数线性增长，而凭证数是运营数据随时会加，配置里没有任何地方提示「加第 6 把凭证会让超时翻倍」；也不取「全局预算跨凭证共享、换凭证也消耗同一份」——那会出现换到第二份时预算已耗尽、第三份根本没试过，那份是好的却没被用上，与配多凭证的目的直接相反。两层各管一件事：内层管抖动，外层管客户端等待上限。

- **M0 透传骨架**：三端点同协议透传 + SSE，硬编码单渠道，对 Anthropic 官方跑通 Claude Code、对百炼/OpenAI 官方跑通 CC 透传。
- **M1 Key + 日志**：鉴权中间件、key CRUD（先用 SQL 手工建）、用量流水。
- **M2 协议转换**：按 §2.1 优先级顺序实现 6 条转换路径（含流式、tool calling、thinking 映射），每条用真实 harness 验收（Claude Code 挂 DeepSeek、Codex 挂第三方、Codex 挂 Anthropic 等）；④ Anthropic→Responses 允许滑出 M2。**另含同候选退避重试（v0.19 提前）**——不依赖多候选，临时闸维持单候选单 key 不放开。
- **M3 管理端**：React 界面覆盖渠道（含模型纳管、凭证池）/ 接入点（含候选与权重）/ key / 用量查询，随后公网部署。**另含凭证池聚合与 key 层内环（v0.38 从 M4 前移）**：凭证逐条 CRUD、多凭证临时闸放开、401 摘除与人工恢复、按凭证归因的日志与用量视图。
- **M4 分流与转移**（v0.12 重排新增，v0.38 缩小）：多候选加权随机分流、候选间故障转移（v0.9）的实现。语义均已拍板，只是实现时点放到纳管成熟后——届时管理端可直接配权重、验分流。**渠道凭证池聚合与 key 层内环（v0.11）已于 v0.38 前移至 M3，不在本里程碑**；同候选退避重试已于 v0.19 前移至 M2，亦不在本里程碑。

M2 是含金量与风险集中点，建议每条转换路径先写「harness 实际发包样本」的对照测试再实现。

**M2 首要参考：sub2api 的 `backend/internal/pkg/apicompat/` 包**（~16k 行含测试，Go，自包含）。它恰好覆盖本项目全部转换路径且方向更全：Responses↔ChatCompletions（含 Codex 事件流测试）、Responses↔Anthropic（含 tool pairing、cache_creation、instructions）、ChatCompletions↔Anthropic bridge、Responses SSE 事件线格式（responses_stream_event_wire）。另外其 `service` 层对 `previous_response_id` 的处理模式可直接借鉴：按 ID 形态分类诊断（openai_previous_response_id.go）、会话失配时删除 `previous_response_id` 改用完整 input 重建上下文（RemovePreviousResponseIDFromBody）、对真 OpenAI 上游用 ID→账号粘连。**注意 sub2api 是 LGPL-3.0：参考实现思路与字段语义没问题，整包复制进闭源/MIT 项目需评估 LGPL 义务（Go 静态链接下实际约等于整项目跟随），个人不分发则无实际影响。**
